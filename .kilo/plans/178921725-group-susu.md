# Group Susu — Implementation Plan

## Context

Group susu (rotating savings) **is the product.** Users create susu groups, contribute weekly, and
rotate receiving the full pot. There is no second feature line.

A *susu* is the oldest financial institution in West Africa: a circle contributes a fixed amount each
week, and each member takes the whole pot in turn. Nobody outside Ghana can build this without
understanding how it actually works, and no platform has shipped it.

## Compliance Gate — read before writing any payment code

Ghana's **Payment Systems and Services Act, 2019 (Act 987) §4(1)** prohibits any body corporate from
operating a payment system or providing a payment service without a Bank of Ghana licence. §4(2)(m)
lists **"provision of any electronic platform for payment or receipt of funds"** as a licensed
activity. §9 makes unlicensed operation a criminal offence.

**An earlier draft of this plan specified escrow — "money held in system." That is the licence
boundary. It has been removed.**

| Gate | Status |
|------|--------|
| Written Act 987 legal opinion | ☐ Not started |
| Agency / aggregator agreement with a licensed DEMI or PSP (Paystack, Hubtel, Moolre, LibertePay, Fincra, dLocal) | ☐ Not started |
| 30% Ghanaian equity (founder qualifies) | ◐ Satisfied |
| Data Protection Commission registration + DPO (Act 843) | ☐ Not started |
| AML/CFT screening design | ☐ Not started |

**Design rule: never take custody of the pot.** Money moves member → mobile money → member. We keep
the *record*, not the funds. Every credible competitor in Ghana and Nigeria publishes the same
sentence — *"we never hold your money"* — and it is free legal risk reduction.

## Decisions Resolved

| Decision | Choice |
|----------|--------|
| Group creation | User-created (not automated) |
| Rotation | Fixed order |
| Frequency | Weekly |
| Miss policy | 1 free skip (turn skipped, pays next round + missed share), removed after 2 misses |
| Platform | App only. **No USSD, no savings pockets, no split-bill.** See master roadmap |
| **Custody** | **Never hold funds. Route collection and payout through a licensed partner. The app is the ledger, not the bank** |
| Payout | Triggered by the licensed rail, not by a button press. Admin cannot release a payout manually |
| Admin role | Administrative only (manage members, verify, flag, restart). **No custody, no withdrawal privileges** |
| Trust model | Server-side verification of every contribution against the rail. Admin accountable for flagging, never debited from a balance we do not hold |
| Contribution amounts | Variable per member (admin sets target, members pay what they can, total must hit target) |
| Cycle restart | Admin decides (group ends after all rounds, admin can refresh/restart) |
| Verification | Server-side, against the payment rail. Never member-typed text, never admin-only |
| Member pricing | **Free, always. No fee on contributions, ever** |

## Monetization Constraints

Free for members, forever. The payer is never the person whose trust we need.

| Tier | Who | Price |
|------|-----|-------|
| Free | Members, admins with up to 5 groups | GH¢0 — no card, no trial clock |
| Collector | Admin running 10–50 groups | GH¢90 / 170 / 350 per month |
| Institution | Credit unions, SACCOs, MFIs, market associations | GH¢1,500 – 8,000 per month |
| Diaspora | Someone abroad funding a group's round | 1.5% of the amount funded |

**Rules we do not break:**
- **Members never pay.** Not a trial, not a small fee. At a 1% take rate the whole national market
  is worth GH¢2.53 per group per month, and the Bank of Ghana suspended a telco's 0.75% transfer
  fee in May 2026 "to protect consumers."
- **No fee on a contribution.** Members are depositing; a fee there reads as a tax on thrift.
- **Admins are free until they run 10+ groups.** A trader with 2 groups is not a business.
- **Keep our name off the contribution line.** If members believe the app takes their money, the
  circle dies.
- **No ads, ever.** Not worth one institutional customer, and it withdraws the trust we sell.

**The money is the Institution tier:** audit trail, PAR / ageing buckets, individual member
statements, BoG-category formatting. 25 paying institutions ≈ breakeven.

Decisions taken during implementation:

- Rounds advance either by a confirmed payout or by an admin closing the round early.
  A closed round below target is recorded as a `skipped` payout and moves the turn on
  without paying anyone.
- `memberShare` is the even pot share (pot / active members) and is what a member is
  charged when they miss, rounded to two decimals.
- Admin trust starts at 100. Each flagged transaction costs 25 and blocks the round;
  the second flag demotes the admin to a regular member.

## Data Model

```python
# susu/models.py
class SusuGroup(models.Model):
    name = models.CharField(max_length=100)
    description = models.TextField(blank=True)
    target_amount = models.DecimalField(max_digits=10, decimal_places=2)  # pot size per round
    total_rounds = models.PositiveIntegerField()  # number of rounds (typically = member count)
    current_round = models.PositiveIntegerField(default=1)
    current_turn_index = models.PositiveIntegerField(default=0)  # index in rotation
    is_active = models.BooleanField(default=True)
    created_by = models.ForeignKey(User, related_name='created_susus')
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    @property
    def pot_size(self):
        return self.target_amount  # fixed per round

    @property
    def is_complete(self):
        return self.current_round > self.total_rounds

class SusuMember(models.Model):
    group = models.ForeignKey(SusuGroup, related_name='members', on_delete=models.CASCADE)
    user = models.ForeignKey(User, related_name='susu_memberships', on_delete=models.CASCADE)
    order = models.PositiveIntegerField()  # position in rotation
    is_active = models.BooleanField(default=True)  # removed after 2 misses
    joined_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        unique_together = ['group', 'user']
        ordering = ['order']

class SusuContribution(models.Model):
    member = models.ForeignKey(SusuMember, related_name='contributions', on_delete=models.CASCADE)
    round_number = models.PositiveIntegerField()
    amount = models.DecimalField(max_digits=10, decimal_places=2)
    mobile_money_provider = models.CharField(max_length=20, choices=[('mtn_momo', 'MTN MoMo'), ('vodafone_cash', 'Vodafone Cash')])
    reference_number = models.CharField(max_length=100)  # mobile money transaction ref
    status = models.CharField(max_length=20, default='pending', choices=[
        ('pending', 'Pending Verification'),
        ('verified', 'Verified'),
        ('failed', 'Failed'),
        ('flagged', 'Flagged for Review'),
    ])
    paid_at = models.DateTimeField(null=True, blank=True)
    verified_at = models.DateTimeField(null=True, blank=True)

class SusuRound(models.Model):
    group = models.ForeignKey(SusuGroup, related_name='rounds', on_delete=models.CASCADE)
    round_number = models.PositiveIntegerField()
    receiver = models.ForeignKey(SusuMember, related_name='received_rounds', on_delete=models.CASCADE)
    payout_amount = models.DecimalField(max_digits=10, decimal_places=2)
    payout_status = models.CharField(max_length=20, default='pending', choices=[
        ('pending', 'Pending - contributions not verified'),
        ('processing', 'Processing'),
        ('completed', 'Completed'),
        ('failed', 'Failed'),
    ])
    payout_reference = models.CharField(max_length=100, null=True, blank=True)
    completed_at = models.DateTimeField(null=True, blank=True)
```

## Backend Changes

### New API Endpoints

| Endpoint | Method | Auth | Description |
|----------|--------|------|-------------|
| `/api/susu/` | GET | JWT | List all susu groups user belongs to (as member or admin) |
| `/api/susu/` | POST | JWT | Create new susu group (name, target_amount, total_rounds, initial members) |
| `/api/susu/{id}/` | GET | JWT | Get susu group details (rounds, members, pot size, next receiver) |
| `/api/susu/{id}/members/` | POST | JWT (admin) | Add member to susu group |
| `/api/susu/{id}/members/{member_id}/` | DELETE | JWT (admin) | Remove member from susu group |
| `/api/susu/{id}/contributions/` | POST | JWT | Member logs contribution (amount, provider, reference) |
| `/api/susu/{id}/verify/` | POST | JWT (admin) | Admin verifies a contribution (or auto-verify via mobile money API) |
| `/api/susu/{id}/payout/` | POST | JWT (system/admin) | Process payout to current round receiver |
| `/api/susu/{id}/restart/` | POST | JWT (admin) | Restart/refresh the cycle |

### Contribution Flow

```python
# POST /api/susu/{id}/contributions/
Request:
{
    "amount": 1000.00,
    "mobile_money_provider": "mtn_momo",
    "reference_number": "MTN123456789"
}

Flow:
1. Verify reference_number with MTN MoMo API (or mark as 'pending')
2. Create SusuContribution with status='pending' or 'verified'
3. Check if all contributions for this round are 'verified'
4. If all verified → trigger payout (auto or admin-triggered)
5. If any 'pending' → payout blocked, status='pending'
```

### Payout Flow

```python
# POST /api/susu/{id}/payout/
Flow:
1. Verify all contributions for current round are 'verified'
2. Get current receiver (SusuMember at current_turn_index)
3. Initiate mobile money transfer to receiver (MTN MoMo / Vodafone Cash)
4. Create SusuRound with payout_status='processing'
5. On transfer success: payout_status='completed', current_round += 1, current_turn_index += 1
6. On transfer failure: payout_status='failed', retry or manual intervention
```

### Verification Auto-Check

```python
# Background task: runs every 5 minutes
# For all 'pending' contributions:
# 1. Query mobile money API with reference_number
# 2. If confirmed → set status='verified'
# 3. If not found after N attempts → set status='failed'
# 4. After all verified → trigger payout
```

### Admin Liability Logic

The app holds no funds, so there is no balance to debit. Accountability is **reputational and
procedural**, not financial — which is also the only version we can legally operate.

```python
# When a contribution cannot be verified, or a member disputes a verified one:
# 1. Mark contribution as 'flagged'
# 2. Block payout for that round until it is resolved
# 3. Record the flag against the admin who verified it
# 4. Admin trust score decreases
# 5. After 2 flagged transactions → admin loses admin privileges
# 6. Group votes for a new admin, or disbands
# 7. The dispute record is permanent and visible to every member
```

**Why not debit the admin:** we hold no money, so there is nothing to debit, and taking a payment
from a member would be an unlicensed payment service. The leverage is visibility and removal, not
clawback. This is also the design that survives a member dispute without us becoming a party to it.

## Key Business Rules

| Rule | Enforcement |
|------|------------|
| Admin sets target amount | Defined at group creation |
| Members pay variable amounts toward target | Each contribution is logged individually |
| Full pot paid to receiver (target_amount) | Payout always sends target_amount |
| **Shortfall blocks the round** | If verified contributions < target, payout does not fire. The round closes and the missed shares are recorded against the non-contributors |
| **Payout fires automatically when verified** | No manual release. Admin has no button that moves money |
| Minimum contribution | 1 GHC (per existing transaction patterns) |
| Max 50 members per susu | Prevents unmanageable groups |
| Unique member per group | No duplicate memberships |
| **Never hold funds** | No escrow, no custody, no float. Collection and payout route through a licensed partner |
| **Optimistic UI may show `pending`, never `verified`** | Verification is server-side only |

## Security

- JWT auth on all endpoints
- Admin-only endpoints: `POST /members/`, `DELETE /members/`, `POST /verify/`, `POST /restart/`, `POST /payout/`
- Payout requires all contributions verified (system check)
- Admin accountability: trust score, permanent dispute record, revocation after 2 flags. **No
  financial clawback** — we hold no funds, so there is nothing to debit, and debiting a member
  would itself be an unlicensed payment service
- Idempotency key on every contribution write, so an offline replay cannot double-post
- `SusuContribution.reference_number` validated against mobile money API
- All amounts server-validated (never trust client)
- `select_for_update()` on round state changes (prevent double payouts)

## Error Handling

| Scenario | Behavior |
|----------|----------|
| Fake/unverifiable reference | Contribution stays 'pending', payout blocked |
| Admin logs fake, gets flagged | Contribution marked 'flagged', round payout blocked, trust score decreases, dispute record is permanent and member-visible |
| Payout fails (transfer error) | Status='failed', retry or admin intervention |
| Member misses week | Turn skipped, owes missed share + current week |
| Member misses 2nd week | Removed from rotation (`is_active=False`) |
| Admin wants to restart | Requires confirm modal. Resets rounds/turns. |
| Target not reached | Payout blocked until all contributions verified |
| Duplicate contribution | Reject — one contribution per member per round |

## Risks

| Risk | Mitigation |
|------|------------|
| Operating without a BoG licence (Act 987) | **No money moves until the legal opinion and licensed-partner agreement are signed.** No custody, no escrow, no float |
| Admin runs off with the pot | **We never hold funds.** Collection and payout route through a licensed partner, there is no balance to steal, and the app has no payout button. Rail reconciliation + member-visible ledger + trust score |
| Fake mobile money references | Verification via telco API + admin review |
| Payout race condition | `select_for_update()` on round state |
| Complex UI overwhelms users | Progressive disclosure; simple cards → detail on tap |
| Low adoption of susu tab | Onboarding tour; highlight during group creation |
